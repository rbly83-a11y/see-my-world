## 2. Part (ii) — Permission-Boundary Specification

Each statement gives: what the interface **MAY claim**, what it must **NEVER claim**, and the **source**. "Interface" includes screens, copy, API responses, error/denial bodies, previews, Passports, explanations, Receipts, tooltips, counts, caches, telemetry, and any other visitor- or owner-visible channel — leakage through any channel is leakage (Architecture Proposal §1.1; CORE-VIS-06).

**B-01 — Token possession ≠ recipient identity (F-01).**
MAY claim: access requires both a valid Invitation token *and* an authenticated visitor credential that resolves server-side to the grant's named recipient, checked on every request.
NEVER claim: that holding, opening, or presenting an Invitation token, link, or URL proves the presenter is the named recipient; never accept a `recipientId` supplied in a body, query, or header claim as identity.
Source: SLICE-BUILD-REPORT §7, F-01 (A-47 blocker, remediated); Charter A-51 §10 adversarial list, item 1.

**B-02 — No Perspective to an unauthorised visitor.**
MAY claim: an authorised visitor, under a currently valid grant, receives the compiled projection for the granted resolution — in slice scope, the preapproved fixture payload bound to the demonstration grant, served verbatim after the grant check.
NEVER claim / never do: show any Perspective, partial view, count, explanation, or existence signal to an uninvited or otherwise unauthorised visitor; an invalid grant yields no Perspective and no partial view.
Anonymous opening (CORE-VIS-02) is **Deferred — pending separate Founder reconciliation and authorization (G-17)**: named-recipient binding is the only accepted access model, anonymous opening has no accepted implementation, and it must not be presented as available or prototyped as if live. This records the current accepted state; it does **not** decide the future of anonymous access.
Source: CORE-PW-01; CORE-VIS-01, CORE-VIS-02; Bible Ch. 17 §17.1, Ch. 19 §19.1; Charter §10, item 2; test S02-02.

**B-03 — No content after revocation or expiry; honest limit of revocation.**
MAY claim: revocation and expiry are server-side facts enforced at the moment of each attempted action; after either, new opens fail, in-progress visitor actions under the grant (including saving further Seeds) are blocked, and caches, indexes, search results, and retained sessions do not extend the grant.
NEVER claim: that revocation or expiry can erase what a visitor already saw, copied, or saved outside the system while the grant was valid. That limit must be stated plainly to the owner. Also never claim a previously loaded page extends a grant.
Source: CORE-LENS-07; Bible Ch. 17 §17.4; invariants 4, 37; Charter §10, item 3; tests S02-05, S02-14.

**B-04 — Denial and error messages leak nothing (ordinary authorization failures only).**
MAY claim: B-04 governs **ordinary authorization failures — the 403 class** in the slice's visitor path: missing token, unknown/forged token, cross-World token, unresolvable/missing/forged visitor credential, recipient mismatch, revoked grant, expired grant, missing World record, missing derived projection, and resolution escalation all fail closed with the same generic body, indistinguishable from one another (denial bodies for the 403 class are byte-identical across causes).
NEVER claim / never do: reveal private topic state, existence, provenance, counts, or the *reason* for denial through a 403, 404, status difference, timing-visible difference, or error text. A 403 must not reveal private topic state; existence must not be learnable from a response (Ch. 22 §22.3 semantics: 403 / 404 / 400 / 409 as specified for corrections, with the no-leak rule governing all).
NEVER claim / never do (quarantine scope line): describe quarantine unavailability as a denial within B-04's meaning, or describe an ordinary 403 denial as unavailability. Quarantine unavailability is a **distinct response class — 503 `PERSPECTIVE_UNAVAILABLE`, governed by B-05** — checked **before** all authorization checks in the accepted implementation. The 503 discloses nothing beyond unavailability: no mismatch detail, no digest, no World data. The accepted response contract is preserved exactly as implemented; this scoping is documentation precision, not a behaviour change, and neither response may be altered merely to make the documentation uniform.
Source: Bible Ch. 22 §22.3; CORE-COR-05; CORE-VIS-06; Charter §10, item 4; SLICE-BUILD-REPORT §7, F-01 (byte-identical denial bodies); test S02-04; accepted Stage 02 source, `getVisitorPerspective()` (quarantine check first, 503; all ordinary authorization failures via the identical `forbidden()` 403).

**Note following B-04 — differentiated expired/revoked messages (open Founder decision; not a boundary statement).** Whether a visitor who has **passed** recipient binding may be shown a differentiated expired/revoked message is an **open Founder decision** (D03-03 coverage item C-3), to be evaluated against the precise authorization and information-disclosure contract. This specification takes no position on it. The generic 403 body governs all visitor presentations meanwhile, and any distinguishing visitor-facing message would require a Founder decision and a charter change request — not a design choice. (This note is unnumbered; the B-01…B-20 set is unchanged. This D03-03 coverage item C-3 is a different item from §4 conflict C-3 in this document, the Explorer dual-surface conflict; neither is renumbered.)

**B-05 — A quarantined projection is never presented as available.**
MAY claim: after a replay/digest mismatch, derived projections are quarantined and unavailable until the mismatch is resolved; owner-authoritative state is untouched. Quarantine's response — **503 `PERSPECTIVE_UNAVAILABLE`** — is the distinct response class scoped **out** of B-04 (see B-04 as amended): it is not a generic denial, and it discloses nothing beyond unavailability.
NEVER claim / never do: present a quarantined projection as available, stale-but-usable, or partially available; serve any visitor fixture for a quarantined World; or present quarantine as overwriting owner state.
Source: CORE-PW-06; invariant 17; Bible Ch. 26 §26.5; Charter §10, item 5; SLICE-BUILD-REPORT §7, F-03; test S02-11.

**B-06 — Logical deletion is never physical erasure.**
MAY claim: **logical deletion** — deletion/invalidation of a World and its derived projections within the prototype's storage boundary, recorded in the deletion manifest, with physical erasure expressly **not** tested.
NEVER claim: "erased," "securely deleted," "wiped," erasure compliance, or any equivalent, for the prototype outcome (C-02). A physical-erasure claim would require its own threat model, storage-stack analysis, and test design, none of which exists in the corpus.
Source: Approval Addendum C-02; Architecture Proposal §6 (R-03); Charter §10, item 6; tests S02-15…S02-17 (logical deletion only).

**B-07 — Prototype-only capabilities are labelled simulated; simulated ≠ live.**
MAY claim: a capability classified **Prototype-only** may be shown as a simulation for evaluation, labelled as simulated wherever shown; a capability classified **Deferred** may be illustrated only when clearly labelled conceptual.
NEVER claim: that a simulated / prototype-only capability is an implemented backend capability, a live service, or production functionality; never silently introduce a new production requirement through an interface. Passing a mock-based test cannot be claimed to establish backend security. A successful prototype must not be represented as a production deployment.
Source: Charter A-51 §2, §4 (scope classification: Existing / Prototype-only / Deferred), §10 (adversarial item 7; test-provenance rule).

**B-08 — Compile, don't hide: the interface is never the permission boundary.**
MAY claim: what a visitor may not receive is excluded at compilation, server-side, before data reaches any interface; privacy is enforced server-side.
NEVER claim / never do: treat visual hiding, collapsing, masking, or client-side filtering as a permission control. A field visually hidden in an interface but whose value was delivered to the client is a privacy failure on the same footing as displaying it.
Source: Invariant 28; CORE-LENS-04 (eight-step server-side sequence); CORE-VIS-01; Architecture Proposal §1.1.

**B-09 — Detail(Output) ≤ Resolution(Grant).**
MAY claim: compilation cannot increase information; the output contains no finer detail than the granted resolution (Continent / Coast / Harbour), structurally — finer data is absent from the payload, not suppressed in display. Presentation compilation likewise cannot increase the information in the authorised projection (invariant 22).
NEVER claim / never do: deliver finer data and rely on presentation to suppress it; use aesthetic choices, map geometry, aggregates, or explanations as a secondary channel for excluded information; or approve a generalised label that traces to a single non-public node without specific, recorded, preview-visible owner approval for that label in that Lens (otherwise generalise further or omit).
Source: Invariant 9; invariant 22; Bible Ch. 18 §18.3, §18.4; CORE-LENS-03, CORE-LENS-06; CORE-VIS-06.

**B-10 — The Worldprint itself is never shared.**
MAY claim: what may be shared is a Lens-derived projection of the Worldprint, compiled under a specific grant.
NEVER claim / never do: share, export, index, cache, or transmit the Worldprint graph itself; copy private evidence into Perspective rows; or allow free-text "why" answers to leave the owner's World or shape another user's draft, suggestions, or comparisons.
Source: CORE-PW-05; invariant 15; Bible Ch. 24 §24.3; Architecture Proposal §4.

**B-11 — Absence is not disagreement.**
MAY claim: a topic, label, or territory absent from a Perspective is absent because it was not included, not testified, not eligible, or was generalised/omitted under the grant — absence carries no stance.
NEVER claim / never do: present absence from a projection, a World, or a visit as disagreement, rejection, refutation, dislike, or a negative signal about the absent subject, or invite a visitor or owner to read it as such. (Contrast REFUTED, which is an explicit owner act — row 21 — and is itself never disclosed.)
Source: Invariant 10 (as cited in the assignment corpus; see also CORE-LENS-05, CORE-LENS-06 on omission/generalisation without disclosure).

**B-12 — Views are not endorsements; visitor behaviour never testifies.**
MAY claim: opening a Perspective, dwelling on an object, or saving a Seed records no approval by either party and no affinity in either World.
NEVER claim / never do: represent a visit as agreement, compatibility, mutual interest, or endorsement; let behavioural signals from a visit testify in any World; or write visitor activity to the testimony ledger.
Source: Invariant 8; CORE-VIS-05; Bible Ch. 19 §19.3; Architecture Proposal §4.

**B-13 — A manifest / digest is not an authorisation token.**
MAY claim: a manifest, digest, Passport, or preview identifies and summarises; access checks occur at request time against current grant state.
NEVER claim / never do: treat possession of a manifest, a canonical digest, a Perspective Passport, a saved reference, or a previously served payload as authorisation to access anything; or skip the request-time grant, recipient-binding, revocation, and expiry checks because a manifest/digest matches.
Source: Invariant 42; CORE-VIS-06; CORE-SEED-03 (a saved reference is not a copy and not a licence, invariant 40).

**B-14 — No claim that the prototype validates a complete Lens Compiler (Q-09; C-01).**
MAY claim: the slice exercises grant enforcement and fixture-payload integrity — visitor disclosure is fixed, synthetic, preapproved fixtures (W-SYN-1; P-SYN-CONTINENT / P-SYN-COAST / P-SYN-HARBOUR), served verbatim after grant checks; it compiles nothing over live owner data.
NEVER claim: that the slice or Stage 03 prototype validates, implements, or privacy-tests a complete / general Lens Compiler. General compilation remains gated on the Q-09 Founder decision. Test **S02-12 is a future compiler test** (C-01): it is not part of the slice's executable acceptance set, cannot be counted as passed by serving a fixture, and a fixture response evidences nothing about compilation, eligibility computation, or resolution-dependent disclosure.
Source: Architecture Proposal §3 (R-01), §5.3 (Q-09); Approval Addendum C-01; CORE-LENS-08 (blocked, Q-09); SLICE-BUILD-REPORT §§2–3, 5.

**B-15 — No CONFIRM operation while Q-01/D-34 is open.**
MAY claim: the correction action set available is exactly the four testimony-v1 operators — BOOST, REDUCE, REJECT, KEEP_WATCHING — labelled provisional in the disputed respect, with BOOST → DECLARED as the v1 rule that governs meanwhile. RESTORE and REMOVE_BUOY exist only as their own separate operations, not as correction types.
NEVER claim / never do: present a separate **CONFIRM** operation as available, freeze the correction action set as final, or imply the CONFIRM conflict is settled. In the slice, submitting CONFIRM (or RESTORE) as a correction type is rejected (400).
Source: CORE-COR-02 (blocked for final semantics, Q-01/D-34); Architecture Proposal §5.3; SLICE-BUILD-REPORT §7 ("Unaddressed / unchanged"); test S02-09.

**B-16 — Silence is not consent; each Perspective stands on its own grant.**
MAY claim: publication requires an explicit owner action for that Perspective; a prior publication is not consent to a later one, and later World changes do not silently alter a published Perspective — republication is a new owner action producing a new version.
NEVER claim / never do: infer consent from silence, inactivity, an earlier grant, or an earlier publication; or silently update a served Perspective when the underlying World changes.
Source: CORE-LENS-01; Bible Ch. 17 §§17.1–17.2.

**B-17 — Testified material only in a pilot Perspective; REFUTED never disclosed.**
MAY claim: in the pilot, a Perspective contains only testified material at the granted resolution.
NEVER claim / never do: include a PROPOSED or WITNESSED node in any Perspective in any form, including as an anonymised or generalised trace; or disclose a REFUTED topic's internal record through a Perspective in any form (invariant 13). The sole corpus exception — owner separately authorised publication of a coastline, as boundary shape only at the granted resolution — must not be presented as disclosure of the refuted topic itself, and its standalone feature status remains deferred (Q-36 note in CORE-LENS-05).
Source: CORE-LENS-05; invariants 13, 20; Bible Ch. 17 §17.2, Ch. 18 §18.2 step 3.

**B-18 — Preview equals payload; "Why is this here?" answered only at resolution.**
MAY claim: the owner preview is rendered from the compiled payload itself — what the owner approves in preview is the most any visitor can receive — and each discovery object answers "Why is this here?" from the projection / permitted Receipts at the granted resolution, or honestly at the level that does exist (e.g. that the owner chose to include this territory).
NEVER claim / never do: show the owner a preview richer or poorer than the visitor payload; answer a visitor's "why" by reaching into private evidence; or let an explanation name, paraphrase, count, or encode what was generalised away.
Source: CORE-LENS-02; CORE-VIS-04; Bible Ch. 18 §18.2 step 7, §18.5; test posture in Architecture Proposal §7 (S02-03).

**B-19 — A Seed is not a copy and not a licence; revocation's Seed effect is exact.**
MAY claim: a Seed holder retains their own notes and any lawful public-resource bookmark after revocation of the source Perspective.
NEVER claim / never do: present a Seed as a copy of, or continuing access to, the source Perspective; retain or serve revoked Perspective content through a Seed; or claim saving a Seed mutates any World (it changes nothing until its holder deliberately acts on it).
Source: CORE-SEED-02…05; invariants 40, 8; Bible Ch. 19 §19.4, Ch. 17 §17.4.

**B-20 — No production, persistence, or identity claims beyond scope.**
MAY claim: the Stage 02 slice is an implemented, locally tested prototype on a provisional stack (Node, `node:sqlite` behind a storage port), not deployed and not production; Stage 03 proves the experience is understandable and usable without claiming production readiness.
NEVER claim / never do: claim production persistence, a confirmed production database, hosting, scale, deployment, public endpoints, a pilot population, or real-world identity verification. The SQLite adapter decides nothing about production persistence.
Source: Charter A-51 §§1–4, 11; CORE-PW-09 (candidacy, blocked on Q-21); README (status line); SLICE-BUILD-REPORT §5.

## 3. Terms Whose Semantics Remain Open

Nothing in this section is resolved by this document. Each item names the open question exactly as the charter requires.

**Open on Q-09 — field-level disclosure schema (CORE-LENS-08).**
- *Lens* — which fields each resolution (Continent / Coast / Harbour) may disclose, field by field. Resolution semantics and disclosure eligibility are specified (Chs. 18, 33); the schema is not. Until Q-09 is settled, the Lens Compiler cannot be built or privacy-tested to acceptance, S02-12 remains a future test (C-01), and no interface may claim per-resolution field disclosure beyond the fixture public bands actually served.
- *Perspective* — the general (non-fixture) compiled content of a Perspective over live owner data.
- *Receipt (visitor form)* and *Perspective Passport* — their final field content insofar as it depends on the per-resolution schema.

**Open on Q-01 / D-34 — CONFIRM conflict (CORE-COR-02).**
- *CONFIRMED (provenance)* — whether confirmation is an explicit CONFIRM event distinct from BOOST, or whether BOOST → DECLARED is the confirmation act. Testimony-v1 (BOOST → DECLARED) governs the normative text meanwhile; it does not settle the conflict.
- *testimony / correction action set* — the final correction UI action set cannot be frozen until Q-01 is settled; any prevailing alternative arrives as a separately versioned reducer, not a rewrite (ledger events record `reducer_version`).
- *provenance labels* — the complete transition table (also Q-06) changes with any Q-01 ruling (CORE-COR-09).

**Open on Q-21 — production persistence (CORE-PW-09).**
- *World / Worldprint persistence* — PostgreSQL / World Schema v2.0 is a recorded **candidacy**, not a confirmed production database. The slice's SQLite adapter behind the storage port is provisional and prejudges nothing.
- *grant / Perspective persistence, replay strategy* — final persistence and event-replay strategy confirmation waits on Q-21. Prototype save/reopen evidence (S02-08) evidences the prototype store only.
- *logical deletion* — mechanics are specified and prototype-tested as logical deletion; retention periods, backup expiration, and any erasure-compliance position additionally wait on Q-13 and, for a physical-erasure claim, on a threat model that does not yet exist (C-02).

**Also open, noted without expansion:** Q-06 (complete provenance transition table), Q-10 (forwarding/resharing), Q-05 (exact visitor flows), Q-13 (retention periods); anonymous opening (CORE-VIS-02) is **Deferred** pending separate Founder reconciliation and authorization (G-17) — see B-02; recording that deferral does not decide the future of anonymous access. These are recorded here because terms above touch them; this document does not treat them as decided either.

## 4. Terminology Conflicts Found Between Sources — Named, Not Smoothed

**C-1 — Territory: Atlas level vs provisional visual term.** Architecture Proposal §2 reads the Founder's "territory" as the Atlas territory level (Continent → Territory → Topic, Bible Ch. 10) and flags that reading FOUNDER-CONFIRM. The adopted OQ-1 disposition and the shipped README instead treat Territory as a *provisional visual grouping* that "is not an Atlas entity and creates no Atlas geography." The PRD additionally uses "Territory View" as a map view (CORE-PW-07, CORE-SEED-06). Three usages coexist. This specification follows the adopted slice disposition (row 8) and flags the Atlas-level and map-view usages wherever they appear; it does not merge them.

**C-2 — Studio: two corpus referents with the same name.** (i) The correction surface (Chs. 7, 22, 25) and (ii) the Presentation Studio (Ch. 44), whose Level 2 is literally named "World Studio" but governs expression, not meaning, and whose pilot inclusion is recorded as proposed, not adopted (Ch. 44 §44.5). OQ-2 adopted (i) for the slice. Referent (ii) remains in the corpus and will collide with (i) in any unqualified use of "Studio" or "World Studio." This specification uses Studio only in sense (i) for Stage 02/03 scope (row 7).

**C-3 — Explorer: visitor experience vs owner map.** Architecture Proposal §2 records two readings — the visitor Perspective experience (CORE-VIS-*) and the owner exploring their own Worldprint map (CORE-PW-07, Concept). OQ-5 adopted *both* surfaces over one core with separate access rules. The single word "Explorer" therefore names two surfaces with different permission boundaries; any unqualified interface label "Explorer" risks implying the visitor surface inherits owner access. This specification requires the surface to be distinguished (row 6, B-02).

**C-4 — CONFIRMED label without a CONFIRM operation.** The provenance label set includes CONFIRMED, and testimony-v1 assigns a confirmation weight (0.6) and entry weights producing CONFIRMED topics in the slice's authoring operation, while simultaneously **no CONFIRM operation exists** and S02-09 asserts its absence. Label, weight, and operation do not align in ordinary language. This is the surface form of Q-01/D-34; it is preserved, not resolved (rows 15–16, B-15).

**C-5 — "reset": draft reset vs lifecycle reset.** CORE-FL-06's *reset* (discard a First Light draft without penalty; Specified, live requirement) and Bible Ch. 16 §16.6's *reset* (Unfinished World lifecycle controls freeze / reset / simplify; Concept, excluded from the slice) are different operations sharing one word. Architecture Proposal §5.1 flags the collision explicitly. Unqualified "reset" in interface copy is ambiguous between an in-scope and an excluded operation.

**C-6 — "erasure" in the PRD vs C-02's prohibition.** CORE-PW-08 is headed "Deletion and erasure" and specifies erasure *mechanics* (tombstones, crypto-shredding, deletion manifest), while Approval Addendum C-02 prohibits describing the prototype's tested outcome as "erased" / "securely deleted" and requires the heading **logical deletion**. Both are correct at different levels — specified mechanics vs tested claim — but an interface that lifts the PRD's vocabulary into a user-facing claim would violate C-02. This specification permits only "logical deletion" for prototype claims (row 24, B-06).

**C-7 — Invitation audience: public-link policy in the corpus vs named-recipient only in the slice.** Bible Ch. 17 §17.2 specifies both recipient grants and link capabilities, and CORE-LENS-09 carries both; OQ-8 adopted (a) named-recipient Invitation only, never a public link, for the slice, and no public-link form exists in the build. Corpus capability and slice scope differ; Stage 03 interface language must follow the slice scope and must not present the corpus's public-link policy as available (row 11).

**C-8 — First Light as journey Step A1 vs the slice's empty World.** The PRD journey begins at First Light (Step A1, Specified), while OQ-4(a) adopted an empty, owner-controlled World for the first slice and the README states "no First Light draft generation." A reader of the PRD alone would expect draft generation; a reader of the slice alone would not. Neither source is wrong; the slice exercises Steps A2–A5 in part, not A1. This specification states the exclusion explicitly (row 20).

**C-9 — README test count is stale against the remediated suite.** The shipped README's Run section says "`npm test` — the S02 acceptance suite (16 tests)" and its Layout line lists S02-01…S02-11, S02-13…S02-17, while SLICE-BUILD-REPORT §7 records the post-A-47 suite as **21 tests, 21 passed** (16 preserved + 5 finding-titled F-01…F-04 tests). The README's visitor-path section does describe the F-01 credential mechanism, so the README is internally part-updated. This specification cites the build report (§7) for suite size and does not repeat the README's "16" as the current total.

**C-10 — Compiler language vs fixture reality.** CORE-LENS-04 and CORE-LENS-06 are Specified requirements, and corpus language routinely speaks of "the compiled payload," "the Compiler," and preview "rendered from the compiled payload itself." In the slice, no general compilation runs: the served payload is a hard-coded fixture prepared against the compiler contract, and LENS-04/LENS-06 are recorded in the build report as "specified but not executed over owner data." Interface or specification language that drops the fixture qualification overclaims implementation. This specification retains the qualification in every affected row and in B-14.
